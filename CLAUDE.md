---

## 1. What This Is

**Chalked In** (working name; originally pitched as "Tough Love") is a solo-built fitness coaching + social app. The core hypothesis being tested: **does an adaptive workout plan combined with visible small-group accountability actually keep people training consistently?** Everything is built around testing that with a small group of friends before any wider launch.

Two core mechanics:
1. **Adaptive plan generation** — a rules-based engine builds a personalized workout split, then adjusts weights/reps over time based on logged performance.
2. **Social accountability** — friend connections and real-time chat, so consistency is visible to people who matter to the user, not just tracked privately.

## 4. Backend Architecture

All files in `src/main/java/com/chalkedin/backend/`. Package declarations must match this exact folder path or you'll get confusing "cannot be resolved to a type" compile errors — this has happened multiple times during development from files landing in `com/chalkedin/` instead of `com/chalkedin/backend/`.

**Core plan generation:**
- `IntakeRequest.java` — DTO for intake form data: `experienceLevel`, `daysPerWeek`, `goal`, `equipmentAccess`, `injuries`, `includeExplosiveTraining`, `splitTypeOverride`, plus optional `squatOneRepMax`/`benchOneRepMax`/`deadliftOneRepMax`. **`overheadPressOneRepMax` removed 2026-09-03** — Overhead Press dropped as a tracked lift (developer's call, three tracked lifts judged sufficient); see the tracked-lifts note under `applyOneRepMaxScaling` below.
- `Exercise.java` / `WorkoutDay.java` / `WorkoutPlan.java` — nested DTOs representing the generated plan
- `ExerciseLibrary.java` — static exercise data (~85 exercises across chest, back, legs, shoulders, biceps, triceps, abs, calves, plus an explosive/plyometric category), each with `full_gym` / `dumbbells_only` / `bodyweight_only` variants. Exercises are randomly selected per generation (`pickRandom`) for variety. **`pickRandom` now takes an optional `mustInclude` exercise name** (added 2026-08-31, see bug note below) — when set, that exercise is always included first before the remaining slots are filled randomly. Wired into `getChestExercises`/`getBackExercises`/`getLegExercises`/`getShoulderExercises` via 3-arg overloads; the other muscle-group pickers don't need it.
- `PlanGeneratorService.java` — the orchestrator:
  - `determineSplitType`: beginner → full_body, intermediate → upper_lower (≤4 days/week) or push_pull_legs (>4), advanced → push_pull_legs. Only picks the split *archetype* — does not determine day count (see bug note below). **Never chooses `pplul`/`arnold_split`** (see below) — those are manual-override-only, this auto logic is intentionally unchanged. **Bypassed entirely when `IntakeRequest.splitTypeOverride` is non-null** (added 2026-09-03) — `generatePlan` checks the override first and only falls back to `determineSplitType` when it's absent, letting the frontend's "Split (optional)" dropdown force a split directly. `buildDays` needed no changes for the original three overrides — it already cycles whatever split pattern it's given across `daysPerWeek`.
  - **Two more split options, added 2026-09-03 after web research into split quality/suitability:** `pplul` (Push/Pull/Legs/Upper/Lower) and `arnold_split` (internal key only, see naming note below) are **fixed-sequence, not cyclable** — `buildDays` returns early for these two before reaching the generic `for i in 1..daysPerWeek` loop, since forcing them to cycle across other day counts would break what defines them. `pplul` is always exactly 5 days regardless of `daysPerWeek` input (reuses `buildPushDay`/`buildPullDay`/`buildLegDay`/`buildUpperDay`/`buildLowerDay`, no new exercise-selection logic needed). `arnold_split` is always exactly 6 days: Chest/Back, Shoulders/Arms, Legs × 2, via two new helpers (`buildChestBackDay`: chest 3 + back 3 + abs 1; `buildShouldersArmsDay`: shoulders 2 + biceps 2 + triceps 2 + abs 1) plus the existing `buildLegDay`. Frontend only shows `pplul` in the picker when `daysPerWeek == 5` and the 6-day one when `daysPerWeek == 6`.
  - **Research finding behind the beginner-suitability warning:** multiple independent sources (Legion, Hevy, Boostcamp, StrengthLog, 1st Phorm, etc.) consistently describe both PPLUL and the 6-day chest/back-shoulders/arms-legs split as intermediate-to-advanced (6-12+ months training experience), not beginner-appropriate — beginners are steered toward full-body or upper/lower at lower frequency instead. Resolved as: available to everyone regardless of experience level (not gated/blocked), but `intake_screen.dart` shows an inline warning when a beginner selects either. Don't remove this warning without revisiting the research that justified it.
  - **Naming note:** the 6-day split is internally keyed `"arnold_split"` (Java code, tests, this doc) but that string is **never shown to users** — deliberately avoided using a real, brand-protective public figure's name as a selectable UI label even though "Arnold Split" itself is common, non-trademarked fitness terminology. The frontend label is purely descriptive: "Chest/Back • Shoulders/Arms • Legs". Keep this distinction if either side gets refactored — user-facing copy stays descriptive, only the backend key stays as-is.
  - `buildDays`: assembles each day's exercises by looping `i` from 1 to `intake.getDaysPerWeek()` and **cycling** through the chosen split's day-type sequence (full_body: every day is "Full Body"; upper_lower: alternates Upper/Lower; push_pull_legs: cycles Push/Pull/Legs) via six small `build*Day` helpers (`buildFullBodyDay`, `buildUpperDay`, `buildLowerDay`, `buildPushDay`, `buildPullDay`, `buildLegDay`), each labeled `"Day " + i + " - <Type>"`. Takes the full `IntakeRequest` (not just `equipmentAccess`) so it can compute `mustIncludeFor(...)` for each of the four tracked lifts and pass it through to the relevant `ExerciseLibrary` pickers on every occurrence of that day type, not just the first.
  - `adjustForGoal`: strength → 4-6 reps/4 sets/scaled weight up ~15%; general_fitness → 12-15 reps/3 sets/scaled down ~20%; hypertrophy uses the library's default 8-12 rep values as-is. **Since 2026-09-03, skips this entirely for anything in `ACCESSORY_EXERCISES`** (see bug #3 below) — those always keep the exercise library's own default reps/sets/weight, regardless of goal.
  - `applyOneRepMaxScaling`: **only fires when `equipmentAccess == "full_gym"`.** Scales the three tracked lifts (Squat/Bench/Deadlift — Overhead Press dropped 2026-09-03) to a percentage of the user's entered 1RM: strength 82%, hypertrophy 72%, general_fitness 60% (grounded in NSCA %1RM-by-rep-range research). Scales the *raw entered 1RM* directly — there is no separate seeded "training max" value (see the corrected section 5 below). **Since 2026-09-03, also handles `FAMILY_RATIOS`** (see bug #3) — non-tracked exercises with a real strength-transfer relationship to a tracked lift get scaled as a ratio of *that* lift's 1RM (e.g. Leg Press at 1.75× squat) when the relevant 1RM was provided; falls back to `adjustForGoal`'s flat-baseline result otherwise.
  - `addExplosiveTraining`: adds 1-2 plyometric exercises to leg-focused days if the toggle was checked — applies per-day by label match, so it already worked correctly across a cycled schedule without changes.

  **Bug found and fixed 2026-08-31 (#1):** `applyOneRepMaxScaling` only scales an exercise if its name exactly matches one of the tracked-lift names. Exercise selection is otherwise fully random per muscle-group pool (e.g. the full-gym leg pool has 6 exercises, only 3 get picked for a given day) — so entering a squat 1RM used to silently do nothing about half the time, because "Barbell Squat" simply wasn't picked that day. Fixed via the `mustInclude` mechanism above: `buildDays` now forces the tracked lift into the relevant pool's picks whenever its 1RM was provided and `equipmentAccess == "full_gym"`. Covered by regression tests in `PlanGeneratorServiceTest` (`generatePlan_squatOneRepMaxForcesBarbellSquatIntoEveryLegDayAndScalesItsWeight`, run 20x to catch flakiness from the shuffle, checks both leg-day occurrences in a 6-day cycle since bug #2 below).

  **Bug found and fixed 2026-08-31 (#2), reported directly by the developer while using the app ("selecting 5 days only creates a 3 day plan"):** `buildDays` used to hardcode a fixed day count per split archetype — always exactly 3 for full_body, 2 for upper_lower, 3 for push_pull_legs — completely ignoring `daysPerWeek` except as the threshold inside `determineSplitType` for picking upper_lower vs push_pull_legs. So e.g. an advanced user selecting 5 or 6 days/week always got exactly 3 days (Push/Pull/Legs once), and an intermediate user selecting 3 days/week with upper_lower always got exactly 2. Fixed by rewriting `buildDays` to loop `daysPerWeek` times and cycle through the split's day-type pattern (see above) — a 6-day advanced plan now correctly produces Push/Pull/Legs/Push/Pull/Legs, a 4-day intermediate upper_lower plan produces Upper/Lower/Upper/Lower, etc. Verified both via the new `PlanGeneratorServiceTest` coverage (`generatePlan_dayCountAlwaysMatchesDaysPerWeek` parameterized across every experience level × 3-6 days, plus renamed/expanded cycling-specific tests) and directly via `curl` against `/api/generate-plan` with `daysPerWeek: 5`, confirming 5 days come back. **This was a significant correctness bug in the core adaptive-plan-generation feature** — worth being extra alert for similar "the number the user picked doesn't actually control what gets generated" mismatches elsewhere (e.g. double-check nothing else silently ignores `daysPerWeek`, `goal`, or `equipmentAccess` in a similar way).

  **Bug found and fixed 2026-09-03 (#4), reported directly by the developer while using the app ("why is that weight so low comparatively to the 1 rep max? i can leg extension the full stack which is 220 pounds"):** a gap left by bug #3's own fix. `ACCESSORY_EXERCISES` and `FAMILY_RATIOS` are independent checks — being in one doesn't exclude an exercise from the other — but `Leg Extension`, `Leg Curl`, and the two full-gym machine calf raises were only ever added to `ACCESSORY_EXERCISES` (correctly protecting their rep ranges from a strength goal's 4-6 rep push) and never to `FAMILY_RATIOS`, so their weight stayed frozen at the exercise library's flat default (50 lbs for Leg Extension) regardless of the lifter's actual squat. Unlike arm/ab isolation work, these four exercises share the same kinetic chain as the squat, so a strength-transfer relationship genuinely exists — fixed by adding them to `FAMILY_RATIOS` too, squat-anchored: Leg Extension 0.70×, Leg Curl 0.45×, Standing Calf Raise (Machine) 1.00×, Seated Calf Raise (Machine) 0.75× (rough estimates like the rest of the table — calf strength in particular varies a lot person-to-person, revisit if they feel off). They stay in `ACCESSORY_EXERCISES` too, unchanged — the two sets solve different problems (rep ranges vs. weight) and an exercise can need both fixes at once, which is exactly what was missed the first time. The dumbbells-only/bodyweight-only calf raise variants were deliberately *not* added — `applyOneRepMaxScaling` only ever runs for `full_gym` equipment, so an entry for those names would be inert. Covered by `generatePlan_legIsolationAccessoriesScaleOffSquatButKeepAccessoryRepRanges`, verifying both the new scaled weight and that accessory rep ranges are still untouched by the strength goal.

  **Extended 2026-09-08, developer's direct ask ("can we adjust how the accessory lifts could go off the 1 rep max... right now flat numbers rather than percentage"):** the same fix applied to the rest of full-gym isolation work. Bench-anchored: Cable Chest Fly 0.20×, Cable Lateral Raise 0.12×, Cable Tricep Pushdown 0.25×, Skull Crushers 0.25×. Deadlift-anchored: Face Pulls 0.20×, Barbell Curl 0.20×, Cable Curl 0.15×, Preacher Curl 0.15×, Cable Crunch 0.12× — **Cable Crunch is the weakest-grounded entry in the whole table**, flagged as such in code: ab/core strength doesn't transfer from deadlift as cleanly as the rest of this map, included anyway as a conservative, directionally-real estimate rather than a flat number, but the first ratio worth revisiting if something feels off. **Deliberately excluded: `Assisted Dip Machine`.** Its "weight" is *assistance* (a counterweight reducing effective bodyweight), so a higher number means an *easier* rep — the opposite direction of every other entry in this table. A simple ratio would prescribe a stronger lifter *more* assistance, which is backwards; left at the library's flat default rather than modeling that incorrectly. All these new entries also stay in `ACCESSORY_EXERCISES`, same reasoning as before. Covered by `generatePlan_upperBodyIsolationAccessoriesScaleOffTheirAnchorButKeepAccessoryRepRanges` and `generatePlan_assistedDipMachineIsNeverRatioScaledSinceItsWeightIsAssistanceNotLoad`.

  **Also discovered while investigating this, worth remembering:** the backend fix for bug #3/#4 sat committed locally for 5 days without being pushed, so the deployed Render backend kept serving the old flat-weight behavior the whole time — reported by the developer as "the weight still doesnt seem to have changed." `git push` doesn't happen automatically; a commit alone never reaches the deployed instance. Double-check `git log origin/mainline..HEAD` (both repos) before telling the developer a backend fix is live.

  **Bug found and fixed 2026-09-03 (#3), reported directly by the developer while using the app ("weights arent making much sense when trying to get stronger"):** two compounding problems. First, `adjustForGoal` forced *every* exercise in a day into the same goal-driven rep/weight scheme, including true isolation work — a strength-goal plan would prescribe a 4-6 rep "heavy" Cable Lateral Raise at 11.5 lbs, which no real program does. Second, non-tracked *compound* exercises (Leg Press, Romanian Deadlift, Barbell Row, etc.) had zero connection to the lifter's actual demonstrated strength — just a flat library baseline times a goal multiplier — so an advanced lifter with a 300 lb squat got a 97.5 lb Romanian Deadlift. Fixed with two new static sets in `PlanGeneratorService`: `ACCESSORY_EXERCISES` (package-private `Set<String>` — true isolation work with no clean strength-transfer relationship: all biceps/most triceps/calves/abs, plus lateral raises, leg curl/extension, face pulls, etc.) is fully excluded from `adjustForGoal`'s goal-based changes, always keeping the library's own default reps/weight. `FAMILY_RATIOS` (`Map<String, RatioFamily>`, `RatioFamily(anchor, ratio)`) covers compound exercises with a real relationship to a tracked lift — e.g. Leg Press at 1.75× squat, Lat Pulldown at 0.50× deadlift, Incline Barbell Bench Press at 0.90× bench — applied in `applyOneRepMaxScaling` only when `full_gym` and the relevant anchor's 1RM was actually provided (falls back to the old flat-baseline behavior otherwise, so nothing regresses for beginners with no known 1RM). Ratios are grounded in published strength-ratio research (dumbbell/incline-vs-flat-bench conversions, leg-press-vs-squat multipliers) plus real reference numbers the developer provided from their own lifts (barbell row vs lat pulldown vs cable row) — reasonable estimates, not lab-precise; revisit specific ratios if they feel off in practice. `ACCESSORY_EXERCISES` is package-private specifically so `PlanGeneratorServiceTest` can assert against the real set instead of a hand-duplicated list that could silently drift out of sync (this happened once already while writing the fix — don't reintroduce a duplicated list). Verified against a real strength-goal plan (squat 300/bench 200/deadlift 350): Incline Bench 180, Machine Shoulder Press 130, Lat Pulldown 175, Walking Lunges 90, all now traceable to the lifter's real strength, while Cable Curl/Leg Curl/Cable Crunch correctly stay at their own default rep ranges instead of being forced to 4-6.

**Logging & adaptive adjustment:**
- `ExerciseLog.java` — one logged exercise's actual performance (`exerciseName`, `sets`, `repsLow`, `repsHigh`, `weight`, `feltRating`: "easy"/"moderate"/"hard"/"failed")
- `WorkoutLogRequest.java` (`dayLabel`, `goal`, `List<ExerciseLog> exercises`) / `WorkoutLogResponse.java` (`List<AdjustmentResult> results`) / `AdjustmentResult.java` (`updatedExercise`, `explanation`) — request/response DTOs
- `AdjustmentService.java` — the core logic. **This is simpler than originally designed** (see corrected section 5): it adjusts each logged exercise's weight/reps based on the feel rating, goal-differentiated:
  - "easy" + bodyweight (weight == 0): +2 reps to both bounds
  - "easy" + weighted + strength goal: fixed increment (+10 lbs lower-body lifts, +5 lbs upper-body) rather than a percentage jump, since percentage-based progression at heavy strength loads moves too fast
  - "easy" + weighted + non-strength goal: weight × 1.05, rounded to nearest 0.5
  - "moderate" / "hard": no change, just an explanation string
  - "failed" + bodyweight: −2 reps, floor of 3
  - "failed" + weighted: weight × 0.9, rounded to nearest 0.5
  - It has **no concept of "training max"** — it never reads or writes `TrainingMaxes`, and treats the tracked lifts no differently from any other exercise except for the lower/upper-body increment split under a strength goal.

**Periodization engine (backend-only, not yet wired to any frontend):**
- `Phase.java` (`name`, `durationWeeks`, `startPercentage`, `endPercentage`), `TrainingProgram.java` (`startDate`, `List<Phase>`), `TrainingMaxes.java` (`squat`/`bench`/`deadlift`/`overheadPress` — **note:** still has an `overheadPress` field even though OHP was dropped as a tracked lift elsewhere 2026-09-03; harmless since this class is unused/unwired to the frontend, but inconsistent if periodization ever gets built out — reconcile then, not touched now since periodization is explicitly on hold), `ProgramWeekResult.java`, `ProgramStatusRequest.java` (`program`, `trainingMaxes`)
- `ProgramCalculationService.java` — given a program's phases and a start date, calculates which phase/week you're currently in (based on elapsed calendar time via `LocalDate.now()`) and computes each tracked lift's weight as `trainingMax × currentPhasePercentage`, linearly interpolated across the phase. Past the end of the last phase, holds at that phase's end percentage and marks `programComplete: true`.
- Exposed at `POST /api/program-status`. Covered by `ProgramCalculationServiceTest` (7 tests: first/last week of a phase, phase transitions, past-program-end hold, single-week phase, weight computation/rounding, missing training maxes). **This is the only place `TrainingMaxes` is actually used anywhere in the codebase** — it's an input the caller must supply, not something the app computes or persists on its own.
- User explicitly said "no rush" on building the UI for this. User wants **flexible, user-defined phases** (not a fixed 2- or 3-phase template) when this eventually gets built.

## 5. Training Max System — BUILT 2026-09-03

Deferred earlier today, then reconsidered the same day (see below for the reversal). Now fully live on both backend and frontend: a training max is seeded at 90% of the user's entered 1RM, day-to-day plan weight scales off *that* rather than the raw 1RM, and workout logging nudges the training max over time (+10/+5 lbs on "easy", ×0.9 on "failed") — the same safety-buffer pattern real percentage-based programs like 5/3/1 use.

**Backend (`chalked-in-backend`):**
- `PlanGeneratorService.TRAINING_MAX_SEED_RATIO = 0.90` — the single constant both seeding and scaling derive from, so they can't drift apart.
- `computeSeededTrainingMaxes(intake)`: for each of squat/bench/deadlift, `full_gym` + that 1RM provided → `roundToNearestFive(oneRepMax * 0.90)`; otherwise null. Called from `generatePlan`, exposed on the response as `WorkoutPlan.trainingMaxes`.
- `applyOneRepMaxScaling`: both the direct tracked-lift path and the `FAMILY_RATIOS` anchor path now multiply through `TRAINING_MAX_SEED_RATIO` before applying the goal percentage / family ratio — so e.g. Leg Press stays coherent with the squat itself (both safety-buffered the same way), not just the tracked lift alone.
- **Real behavior change, worth remembering:** every full-gym scaled number is now ~10% lower than it would've been under the old raw-1RM-direct formula (e.g. strength 82% of 1RM → 82% of 90% of 1RM ≈ 73.8% of 1RM). This is the *intended* effect of a safety-buffered system, not a bug — the "squat 300/bench 200/deadlift 350" numbers verified earlier today are now all somewhat lower, on purpose. Verified by hand against real `curl` responses (e.g. squat 300 → training max 270 → strength weight 220; Leg Press → squat training max 270 × 1.75 = 475).
- `AdjustmentService`: the easy/moderate/hard/failed weight-delta logic was refactored into a shared `applyFeltRatingToWeight(baseWeight, rating, isStrengthGoal, isLowerBody)` helper, since the training-max nudge needs the *identical rule* applied to a *different base number* (the stored training max, not the exercise's displayed weight) — `adjustExercise`'s own behavior/output is unchanged. `processLog` separately nudges `WorkoutLogRequest.trainingMaxes` (whatever the frontend sends as currently stored) for any of the three tracked lifts that were logged with an "easy" or "failed" rating, returning the changed ones (only) on `WorkoutLogResponse.trainingMaxes` — null/partial when nothing tracked was logged or no current value existed to nudge from. "moderate"/"hard" are a deliberate no-op, same as the per-exercise path.
- `TrainingMaxes.java` dropped its stale `overheadPress` field (OHP hasn't been tracked since 2026-09-03 — this reconciles the exact inconsistency flagged earlier today). `ProgramCalculationService`'s weight computation for the periodization engine no longer has an Overhead Press case either — down to the three tracked lifts everywhere.
- Tests: `PlanGeneratorServiceTest` (4 new: seeding math, partial seeding, not-full-gym, no-1RM-provided; 2 existing numeric assertions updated for the new ×0.90 layer), `AdjustmentServiceTest` (6 new: easy/failed nudge math, moderate/hard no-op, no-current-value no-op, non-tracked-exercise no-op, multiple lifts in one request), `ProgramCalculationServiceTest` (1 renamed, OHP assertion removed). 65 backend tests total (up from 55).

**Frontend (`toughlove-app`):**
- New `lib/training_maxes.dart` — `TrainingMaxes {squat, bench, deadlift}`, `fromJson`/`toJson`, `isEmpty`, and `mergedWith` (used for the read-merge-write below). 7 new tests in `test/training_maxes_test.dart`.
- `workout_plan.dart` — `WorkoutPlan.trainingMaxes` (nullable), parsed from the generate-plan response.
- `firestore_service.dart`:
  - `saveIntakeAndPlan` now also writes a top-level `trainingMaxes` field (always, even all-null) from `plan.trainingMaxes` — re-running intake with a fresh 1RM deliberately **re-seeds (overwrites)**, not merges, matching "a fresh entry represents current truth."
  - New `getTrainingMaxes()` (reads the field back) and `updateTrainingMaxes(updates)` (nudges after a log). `updateTrainingMaxes` deliberately **reads the current value, merges client-side via `TrainingMaxes.mergedWith`, then writes the complete merged map back** rather than relying on Firestore's own nested-map merge semantics under `SetOptions(merge:true)` — this project has already been bitten once by a merge edge case wiping out sibling fields (section 7), so this sidesteps that risk entirely for a nested object field rather than assuming the safe behavior.
- `intake_screen.dart` needed **no changes** — `plan` was already passed through to `saveIntakeAndPlan` as a whole object, so `plan.trainingMaxes` flows through for free once `WorkoutPlan.fromJson` parses it.
- `workout_log_screen.dart` — fetches current `TrainingMaxes` once in `initState` (`late final Future<TrainingMaxes?> _trainingMaxesFuture`), `await`s it inside `_submitLog` (avoids any race with the async load) and sends it as `trainingMaxes` in the `/api/log-workout` body; after a successful submit, persists any non-null `trainingMaxes` from the response via `updateTrainingMaxes`. No new visible UI — deliberately deferred to the periodization UI step, which needs a place to show these numbers anyway.

**Reversal note:** this was deferred earlier today (2026-09-03) with the reasoning that the ratio-scaling system already fixes the reported problem and a training max's real value only shows up over a longer time horizon than the friend test. The developer reconsidered the same day and asked for it to be built for real after all, alongside streaks and periodization UI. ## 6. Frontend Architecture

All files in `lib/`.

**App entry & auth:**
- **Auth model changed 2026-08-31: real email/password accounts, not anonymous.** Originally the app used Firebase Anonymous Auth (silent, no login screen — a stable UID per device). Since each friend-test participant uses their own device, and anonymous auth has no way to recover an account if local data is ever cleared, switched to real Firebase email/password accounts instead. `main.dart` no longer calls `signInAnonymously()` — it just initializes Firebase and renders `StartupScreen`, which now gates everything behind auth state.
- `auth_screen.dart` — **new 2026-08-31.** Combined sign-up/log-in screen (a single `_isSignUp` toggle switches the button/copy between modes) with email + password fields, calling `FirebaseAuth.instance.createUserWithEmailAndPassword` or `signInWithEmailAndPassword`. Shows `FirebaseAuthException.message` inline on failure. Doesn't navigate directly on success — `StartupScreen`'s `authStateChanges()` stream picks up the new signed-in state and reroutes automatically.
- `startup_screen.dart` — the outer `StartupScreen` is a `StreamBuilder<User?>` on `FirebaseAuth.instance.authStateChanges()`: no signed-in user → `AuthScreen`; signed in → `_ProfileRouter` (private `StatefulWidget`, same file). `_ProfileRouter` holds the profile/plan-resume logic: checks `UserProfileService.getProfile()` — no profile → `ProfileSetupScreen`; profile but no `currentPlan` → `IntakeScreen`; profile with a `currentPlan` → parses it and goes to **`MainTabScreen`** (replaced `HomeScreen` 2026-09-03, see below).
- `user_profile_service.dart` — generates a random 6-character friend code, creates/reads the user's profile doc. Unchanged by the auth switch — it already worked off `FirebaseAuth.instance.currentUser?.uid`, which now just happens to be a real account's UID instead of an anonymous one.
- `profile_setup_screen.dart` — simple display-name entry, first screen a new (now real-account) user sees after signing up. Unchanged.
- `api_config.dart` — single `apiBaseUrl` constant, currently `https://chalked-in-backend.onrender.com`. Every screen that calls the backend (`intake_screen.dart`, `workout_log_screen.dart`) imports this instead of hardcoding the URL — change it here alone to point at a different backend.
- **Manual setup required:** Email/Password sign-in must be enabled in the Firebase console (Authentication → Sign-in method → Email/Password → Enable) for account creation/login to work at all. Not something that can be verified or toggled from code.

**Tab navigation (replaced `home_screen.dart` entirely, 2026-09-03):**
- `main_tab_screen.dart` — **new.** The app's real hub for a returning user with a plan: a `Scaffold` with a Material 3 `NavigationBar` (4 tabs — Training/Progress/Social/Profile) over an `IndexedStack` so every tab's state survives switching between them. Built once in `initState()` from `plan`/`goal` (same constructor shape `HomeScreen` used to take) — `PlanScreen(plan:, goal:)`, `ProgressScreen`, `FriendsScreen` (reused as-is for Social), `ProfileScreen`. A `GlobalKey<ProgressScreenState>` lets `_onDestinationSelected` call `reload()` on the Progress tab specifically when it's selected — see the Progress-refresh bug note below for why that's necessary. A "Gym" fifth tab (map + gym ratings) was discussed and explicitly deferred — not scoped, not needed to validate the app's core hypothesis at this stage; noted for later.
- `plan_screen.dart` (Training tab) — Friends/Logout app-bar icons removed (Social and Profile are now separate tabs); a "Generate new plan" icon action added in their place, using the same confirmation-dialog pattern `HomeScreen` used to have (replaces the current plan, so confirm first, then pushes `IntakeScreen`). Otherwise unchanged: `StatefulWidget` holding a mutable `_days` list, "Log this workout" per day pushes `WorkoutLogScreen` and updates `_days` via `setState` on return.
- `progress_screen.dart` — **new.** Two sections: a reverse-chronological workout history list (`FirestoreService.getLogs()`, new method — queries `users/{uid}/logs` ordered by `loggedAt` descending), and a tracked-lift weight-trend line chart (`fl_chart` package, new dependency) built from the same log data via `tracked_lift_series.dart`'s pure `extractTrackedLiftSeries(logs)` function (`WeightPoint(date, weight)` per tracked lift, sorted oldest-to-newest — kept as a standalone pure function specifically so it's unit-testable without Firestore/widget mocking, see `test/tracked_lift_series_test.dart`). Chart uses the `dataviz` skill's validated categorical palette (slots 1-3: blue/orange/aqua for Squat/Bench/Deadlift, light+dark variants) and mark specs (2px lines, ≥8px end-dots with a surface-color ring, hairline recessive gridlines, a legend since ≥2 series, `LineTouchTooltipData` for the interactive layer) rather than ad hoc styling — load that skill again before touching this chart's visual design. Empty state (no logs yet) and no-tracked-lift-data-yet state are both handled explicitly. **`Overhead Press` removed from tracked lifts 2026-09-03** — see backend section 4; `trackedLiftNames` in `tracked_lift_series.dart` now only has the three.
  - **Bug found and fixed 2026-09-03, reported directly by the developer ("after logging the workout, it doesnt show up in the progress tab"):** `MainTabScreen`'s `IndexedStack` keeps every tab's `State` alive across switches (that's the point — preserves scroll position, in-progress state), which means `ProgressScreen`'s `initState()`-time log fetch only ever ran once, at app startup, not every time the tab was revisited. Fixed by exposing a public `reload()` method on `ProgressScreenState` (renamed from private `_ProgressScreenState` so `main_tab_screen.dart` can reference it) and having `MainTabScreen` call it via the `GlobalKey` whenever the Progress tab is selected. **Worth remembering for any future tab:** `IndexedStack`-based tab persistence needs an explicit "refresh on reselect" hook for anything showing data that can change while the tab is backgrounded — it will not happen automatically.
  - **Bug found and fixed 2026-09-03, reported directly by the developer ("why is the progress page repeating the date? why not just put a data point for 1 day"):** two compounding causes. First, `extractTrackedLiftSeries` added one point per *logged occurrence* with no per-day dedup — logging the same tracked lift twice in one day produced two points on the same calendar date. Second, and the more visible symptom: `fl_chart`'s automatic x-axis tick spacing has no notion of a calendar day — left to its own default interval it can (and did) place multiple ticks within a single day, which all format to the identical "month/day" label regardless of whether the underlying data was deduped. Fixed both: `extractTrackedLiftSeries` now groups by `(lift, calendar day)` and keeps only the latest entry per day (see the new `DateTime(year,month,day)` truncated key in `tracked_lift_series.dart`); `_WeightTrendChart` in `progress_screen.dart` now computes an explicit `interval` for the bottom axis (`_tickInterval`, private to that widget) that's floored at one full day and otherwise aims for ~5 ticks across the visible range, so no two ticks can ever land on the same calendar date. Covered by two new `tracked_lift_series_test.dart` cases (same-day logs collapse to one point keeping the latest; different-day logs stay separate).
- `profile_screen.dart` — **new.** Minimal: display name (read-only, via `UserProfileService().getProfile()`), account email, sign-out button (same `signOut()` + `popUntil((route) => route.isFirst)` pattern `PlanScreen`'s used to have). No name-editing UI — wasn't asked for, no existing edit path to build on.

**Core flow:**
- `intake_screen.dart` — the main form (experience/days/split/goal/equipment/injuries/explosive-training toggle). 1RM fields only render conditionally (`intermediate`/`advanced` experience + `full_gym` equipment) and only for Squat/Bench/Deadlift — **the Overhead Press 1RM field was removed 2026-09-03** along with OHP as a tracked lift generally (see backend section 4). **"Split (optional)" dropdown**: Auto (default, `null` → backend's existing experience+days logic) / Full Body / Upper-Lower / Push-Pull-Legs always available, plus PPLUL (only shown when `daysPerWeek == 5`) and a descriptively-labeled 6-day split (only shown when `daysPerWeek == 6` — see backend section 4 for the naming rationale) with an inline beginner-suitability warning for those last two. Sent as `splitTypeOverride`. Submits to `/api/generate-plan`, saves via `FirestoreService.saveIntakeAndPlan`, navigates via `Navigator.pushReplacement` to **`MainTabScreen(plan:, goal:)`** (changed from a bare `PlanScreen` 2026-09-03 so both first-time and regenerated plans land back inside the tab shell, not a disconnected screen with no nav bar).
- `workout_plan.dart` / `workout_day.dart` / `exercise.dart` / `adjustment_result.dart` — Dart model classes mirroring the backend DTOs, each with a `fromJson` factory.
- `workout_log_screen.dart` — the workout-logging screen. Two-phase UI in one `StatefulWidget`: an input phase (per-exercise weight `TextField` pre-filled with the planned weight — **widened 80→110px 2026-09-03**, was cramped — plus Easy/Moderate/Hard/Couldn't-finish `ChoiceChip`s defaulting to "moderate") and, after submit, a results phase showing each exercise's updated sets/reps/weight (**the backend's per-exercise explanation text was removed from this view 2026-09-03** — developer's call, wanted just the numbers; the backend still returns `explanation`, it's just not displayed here anymore). On successful submit it POSTs to `/api/log-workout`, then calls `FirestoreService.saveWorkoutLog` (writes a `logs` entry) and `FirestoreService.updateDayExercises` (updates `currentPlan.days` in place) before showing results. Tapping "Done" pops back to `PlanScreen` with the updated `WorkoutDay` as the navigation result.
- `firestore_service.dart` — central Firestore read/write logic: `saveIntakeAndPlan` (uses `merge: true`), `saveWorkoutLog` (adds a doc to `users/{uid}/logs`), `updateDayExercises` (reads `currentPlan`, replaces the matching day's exercises by `dayLabel`, writes back with `merge: true`), and **new 2026-09-03**: `getLogs()` (reads the full `logs` subcollection, newest first, for the Progress tab). No training-max methods exist — see section 5, that system was never designed into the frontend either.

**Social layer (now the Social tab):**
- `friend_service.dart` — send/accept/decline friend requests by code, fetch friends list. Uses `arrayUnion` to add each user to the other's `friends` array on acceptance.
- `friends_screen.dart` — own code display, add-by-code input, pending requests, friends list (tap a friend to open chat). **Since 2026-09-03, also shows a `🔥 N day streak` subtitle on each friend** (nothing shown when 0) — `_loadData()` fetches each friend's streak via `StreakService().getStreakWith(uid)` in parallel (`Future.wait`) alongside the existing friend-list load.
- `chat_service.dart` — deterministic conversation IDs (sorted UID pair joined with `_`), real-time messages via `.snapshots()` streams. `_conversationId` **promoted to public `conversationId` 2026-09-03** so `streak_service.dart` can address the same conversation doc without duplicating the sort-and-join logic.
- `chat_screen.dart` — live chat UI using `StreamBuilder`. **Since 2026-09-03**, `_send()` now guards against empty/whitespace-only input before sending (previously relied on `ChatService.sendMessage`'s own internal empty check, which meant a `.then()` callback would still fire even when nothing was actually sent) and touches the streak with that friend once the message send completes.
- `streak_logic.dart` (new) — pure date-math: `dateKey(DateTime)` (`"YYYY-MM-DD"`, local time), `computeNextStreak(currentStreak, lastStreakDate, today, yesterday)`, `isStreakAlive(lastStreakDate, today, yesterday)`. Kept separate from Firestore code specifically so it's unit-testable without mocking — same pattern as `tracked_lift_series.dart`. See `test/streak_logic_test.dart` (10 tests: formatting, same-day no-op, consecutive-day increment, multi-day-gap reset, alive/dead boundary cases).
- `streak_service.dart` (new) — `touchStreakWithFriend(friendUid)` goes through `ChatService.getOrCreateConversation` first (so a conversation whose *first* activity is a workout log still gets its full normal field set — `createdAt`/`lastMessage`/`lastMessageAt` — rather than a partial doc that `getOrCreateConversation` would later skip filling in because it already exists), then runs a Firestore transaction updating `streakCount`/`lastStreakDate` on that conversation doc via `computeNextStreak`. `touchStreakWithAllFriends(uids)` loops that for every friend — needed because "I logged a workout" is a fact about *one person*, global across all their friendships, unlike a chat message which is already scoped to one conversation. `getStreakWith(friendUid)` reads the count back, returning `0` if `isStreakAlive` says it's gone stale rather than showing a leftover number.
- `workout_log_screen.dart` — **since 2026-09-03**, after a successful log submit, fetches the current friends list and fire-and-forgets (`unawaited`) `StreakService().touchStreakWithAllFriends(...)` so the results screen isn't blocked on a handful of Firestore writes.

**A recurring bug pattern worth knowing about:** throughout development, files were repeatedly "created" in conversation but didn't actually save (0-byte files) or landed in the wrong folder. Always verify with `ls -la` before assuming new code compiles or exists — this has cost real debugging time more than once.

**Tests:** `test/adjustment_result_test.dart` (2 tests) covers `AdjustmentResult.fromJson` parsing. `test/tracked_lift_series_test.dart` (4 tests, added 2026-09-03) covers `extractTrackedLiftSeries` — sorting, ignoring non-tracked exercises, omitting lifts with no data, empty input; uses `Timestamp.fromDate(...)` directly, confirming `cloud_firestore`'s `Timestamp` type works fine in a pure unit test with no Firebase initialization needed. Screen-level testing (the `WorkoutLogScreen`/`PlanScreen`/`AuthScreen`/`MainTabScreen` flows) would still need HTTP-client and Firebase-auth/Firestore mocking infrastructure that isn't set up in this project yet (e.g. `mocktail`, `firebase_auth_mocks`, `fake_cloud_firestore`) — worth adding if deeper frontend test coverage becomes a priority.

## 7. Firestore Data Model

```
users/{uid}
  experienceLevel, daysPerWeek, goal, equipmentAccess, injuries, createdAt
  displayName, friendCode, friends: [uid, uid, ...]
  currentPlan: { splitType, days: [{ dayLabel, exercises: [{name, sets, repsLow, repsHigh, weight}, ...] }] }

users/{uid}/logs/{logId}
  dayLabel, loggedAt, exercises: [{name, sets, repsLow, repsHigh, weight}, ...]

friendRequests/{requestId}
  fromUid, fromDisplayName, toUid, status ("pending"/"accepted"/"declined"), createdAt

conversations/{conversationId}       // id = sorted UIDs joined with "_"
  participants: [uid, uid], createdAt, lastMessage, lastMessageAt
  streakCount, lastStreakDate         // added 2026-09-03, see section 6/8

conversations/{conversationId}/messages/{messageId}
  senderUid, text, sentAt
```

**No `trainingMaxes` field exists anywhere** — see section 5's correction.

**Important:** all Firestore writes to the user doc use `SetOptions(merge: true)`, including the new `updateDayExercises` method. Without this, later writes silently wipe out earlier fields (e.g. `displayName`, `friendCode`) — this was a real bug caught and fixed during development. Keep using `merge: true` for any new fields added to the user doc.

## 8. Key Design Decisions (with reasoning, so they aren't re-litigated or accidentally reversed)

- **Rep ranges and 1RM percentages are grounded in NSCA training-load research**, not guessed: strength 1-5 reps/85-100% 1RM, hypertrophy 6-12 reps/67-85%, endurance 15+/under 67%. App's specific values: strength 4-6 reps @ 82%, hypertrophy 8-12 @ 72%, general fitness 12-15 @ 60%.
- **Gender is deliberately NOT collected or used as an input.** Real sex-based strength differences are well documented (upper-body differences are larger than lower-body differences, on average), but once a real 1RM exists, it already encodes the individual's actual strength — a far more precise signal than a demographic average. Gender was considered only as a *hypothetical* fallback for users with no known 1RM, and ultimately not implemented at all.
- **Explosive/plyometric training is a generic opt-in toggle**, not tied to any specific sport (originally proposed for volleyball players specifically, generalized on request). Added to leg-focused days only.
- **Streaks — built 2026-09-03** (reversed from "deferred to after the friend test," alongside training-max and periodization UI, same day). Design as originally confirmed: a streak between two friends stays alive if **either** a logged workout **or** a chat message happens that day (not requiring both, unlike literal Snapchat streaks) — chosen specifically so streaks don't strictly depend on the logging feature and don't unfairly break on a planned rest day. See section 6 (`streak_logic.dart`/`streak_service.dart`) for the implementation — stored as two extra fields (`streakCount`, `lastStreakDate`) directly on the existing per-pair `conversations/{id}` doc rather than a new collection, since a streak is exactly as pair-scoped as a conversation already is.
- **Wearable integration (Apple Watch/Garmin/Oura) is deferred to after the friend test.** Reasoning: each is a separate SDK/developer program with no shared code, and wearables don't reliably auto-capture structured strength training data anyway — better to revisit once logging exists and the core concept is validated with real users.
- **Visual design pass done 2026-08-31** (originally deferred until core features were done — logging + auth were both solid by this point, and seeing the live app with default theming prompted doing it now rather than waiting further). Central `ThemeData` in `main.dart`: `ColorScheme.fromSeed` with an "ember" orange-red seed (`0xFFE8552E`, replacing the leftover `deepPurple` from `flutter create`), light + dark variants via `ThemeMode.system`, custom component themes for `AppBar`/`Card`/`ElevatedButton`/`TextField`/`Chip` so every screen inherits a consistent look automatically. Also hand-touched: `auth_screen.dart` and `profile_setup_screen.dart` got a centered branded layout with an icon + headline; `plan_screen.dart`'s exercise rows got a name + sets/reps/weight badge layout with a per-split-type icon; `friends_screen.dart`'s friend code became a highlighted badge; `chat_screen.dart`'s message bubbles were switched from hardcoded `Colors.deepPurple`/`grey[300]` to theme colors (`colorScheme.primary`/`surfaceContainerHighest`) so they actually respect the new theme and dark mode. `intake_screen.dart`'s long flat form was grouped into three `Card` sections ("Your training" / "Known 1-rep maxes" / "Anything else") for readability. As a side effect of touching `intake_screen.dart`, also fixed the pre-existing `avoid_print` and deprecated-`value:`-on-`DropdownButtonFormField` lint warnings — `flutter analyze` is fully clean (0 issues) for the first time this session.
- **Unit tests are now a deliberate habit, not an afterthought** (established 2026-08-31, after discovering the backend had zero real coverage). Pair tests with new non-trivial logic in the same pass, in both repos.
- **Switched from Anonymous Auth to real email/password accounts** (2026-08-31). Anonymous auth only persisted identity locally on one device with no way to recover it — fine in theory, but every friend-test participant uses their own device long-term, and losing local storage (reinstall, cleared browser data, new phone) would mean losing access to their account permanently with no recourse. Real accounts cost a small amount of signup friction but make the account actually recoverable. Considered account-linking (keep anonymous-first UX, let people optionally attach a credential later) as a lower-friction alternative but went with a clean replacement instead for simplicity.
- **Gym map + ratings feature deferred, twice** (first 2026-09-01, reconsidered and deferred again 2026-09-03 while scoping the tab navigation). Doesn't serve either core pillar of the app (adaptive plans or visible friend accountability) — it's an adjacent discovery/social feature, not something that tests the actual hypothesis. At the scale of a 4-6 person friend test, a gym-rating map would have only a handful of pins from people who mostly already know where everyone trains, so the feature's core value proposition (discovering/comparing gyms across a broad pool) doesn't really show up yet. Matches the same reasoning already applied to streaks and wearables. If it comes up a third time, treat that as a signal worth taking seriously rather than deferring by default — but it hasn't yet.
- **Overhead Press dropped as a tracked lift** (2026-09-03, developer's direct call — "we can get rid of overhead press in the known 1rep max honestly"). Considered narrowing to just the intake-form field vs. removing it everywhere; went with everywhere specifically to avoid leaving backend `mustInclude`/1RM-scaling code for OHP that could never fire once the frontend stopped sending it. Squat/Bench/Deadlift remain tracked; Overhead Press still exists as a normal exercise in the library, just no longer 1RM-tracked or force-included.
- **Non-tracked exercise weights now scale off a ratio of the relevant tracked lift, not a flat library baseline** (2026-09-03). Grounded in web-researched strength ratios (dumbbell/incline-vs-flat-bench conversions, leg-press-vs-squat multipliers, general squat:bench:deadlift ratios) plus real reference numbers the developer provided from their own training (barbell row vs. lat pulldown vs. cable row). Paired with excluding true isolation work from goal-based rep/weight changes entirely, so a "strength" goal no longer prescribes nonsensical things like a 4-6 rep max lateral raise. See section 4, bug #3, for the full mechanism (`FAMILY_RATIOS`/`ACCESSORY_EXERCISES`).
- **Real app icon shipped 2026-09-03**, replacing Flutter's default generated icon on both platforms. Concept: a chalked handprint (palm + five fingers, a few small chalk-dust flecks near the fingertips) in warm off-white on the app's exact ember seed color (`0xFFE8552E`, matching `main.dart`'s `ColorScheme.fromSeed` and the privacy policy's palette), on a radial "spotlight" gradient background. Deliberately not a barbell/dumbbell silhouette — that's the generic default nearly every fitness app icon reaches for; a handprint is specific to this app's actual name ("Chalked In" — chalking hands before a lift) and distinctive in an app-grid context. Built procedurally (Python/Pillow, direct trigonometric polygon math per finger rather than hand-rotating pre-drawn shapes, for precise/reviewable geometry) since no image-generation tool was available; source lives at `assets/icon/icon.png` (1024×1024, RGB, no alpha). Regenerated into both platforms via `flutter_launcher_icons` (config lives in `pubspec.yaml` under the `flutter_launcher_icons:` key — re-run `dart run flutter_launcher_icons` after replacing `assets/icon/icon.png` if the design ever changes). **Single flat icon only, not a true Android adaptive icon** (no separate foreground/background layers) — acceptable since Android is currently deprioritized (see section 10); worth revisiting if Android testers join later, since adaptive icons render better across different Android launchers' masks.

## 9. Testing Methodology (how this project actually gets verified — use this, don't reinvent it)

Established through this project's development; use these approaches rather than defaulting to something else (like introducing browser-automation tooling — Playwright/chromium-cli are not part of this project's workflow).

- **Backend logic in isolation**, before wiring up the frontend or when debugging backend-only behavior:
  ```bash
  curl -X POST http://localhost:8080/api/generate-plan \
    -H "Content-Type: application/json" \
    -d '{"experienceLevel":"advanced", ...}'
  ```
  Pipe through `python -m json.tool` when the raw output is too dense to read. Lets you verify split logic, 1RM scaling, and adjustment math directly against real JSON responses without clicking through the UI each time.

- **Backend compiles/runs cleanly:**
  ```bash
  ./mvnw spring-boot:run
  ```
  Watch for "Started BackendApplication" in the logs before testing anything downstream. (`./mvnw compile` alone is faster for a pure compile check; the test suite runs via `./mvnw test` — see section 4 for what's covered.)

- **Frontend, manual click-through** — the default way to verify UI changes on this project:
  ```bash
  flutter run
  ```
  Pick a target (Chrome, Windows desktop, Android emulator, or iOS simulator depending on the machine), then actually fill out the form/tap the buttons and watch the terminal for print statements or errors. Use `R` (capital, hot restart) rather than `r` (hot reload) whenever changes touch `main.dart` or anything at startup — hot reload doesn't reliably pick those up.

- **Firestore — never trust "should have worked," always check the real data.** Open the actual Firebase Console → Firestore Database and look at what landed in the `users` collection, confirming fields are actually there. This is exactly how the missing-`merge: true` bug (section 7) got caught.

- **Multi-user features specifically (friends, chat):** run two separate browser identities side by side — a regular Chrome window plus an Incognito window — since each gets its own independent anonymous Firebase Auth UID. Simulates two different people sending friend requests or chatting in real time and lets you watch both sides update live.

- **File integrity, before assuming anything would even compile:**
  ```bash
  ls -la path/to/file.java
  ```
  Given how many times a file got "created" in conversation but landed empty or in the wrong folder (see section 6), checking byte size and location first saves a lot of confused debugging later.

- **When something gets persistently, weirdly stuck:**
  ```bash
  flutter clean && flutter pub get && flutter run
  ```
  Full clean rebuild to rule out stale build cache before assuming the code itself is wrong.

**Known gotcha (iOS Simulator + Keychain):** installing a build via `xcrun simctl install`/`launch` after building with `flutter build ios --simulator --no-codesign` can produce a Keychain access error specifically when Firebase Auth tries to read an existing signed-in session (login fails; fresh sign-up can look fine since it doesn't need to *read* a prior session). Root cause: Firebase Auth's iOS SDK needs a properly resolved keychain-access-group entitlement, which an unsigned build doesn't reliably get. Fix: drop `--no-codesign` (plain `flutter build ios --simulator`, or just `flutter run`, handles simulator signing correctly) and reinstall.

**Known gotcha (Render + Docker + PORT), fixed 2026-09-01:** the first deploy attempt built and started cleanly (logs showed `Started BackendApplication`, no errors) but was completely unreachable — every request got `x-render-routing: no-server` from Render's edge, not an app-level 404. Root cause: `server.port` was set to `${PORT:8080}`, dynamically honoring whatever `PORT` Render injected at runtime (observed as `10000` in the logs) — but Render's routing layer for this Docker service targets the port declared via the Dockerfile's `EXPOSE` line (`8080`), not whatever the app happens to bind to. Fix: pinned `server.port=8080` instead of dynamically reading `PORT` — don't reintroduce dynamic PORT-reading for this service without also confirming it against Render's actual routing behavior.

**Known gotcha (concurrent automated tooling), 2026-09-03:** at one point this session, GitHub's App Modernization tool ("appmod") was actively running a Java 21→25 upgrade against this same local `chalked-in-backend` working directory concurrently with normal development — it created and checked out its own branch (`appmod/java-upgrade-*`) mid-session, which caused a commit to briefly land in the wrong place. Nothing was lost (recovered via a backup branch + careful `git reset`), but if multiple automated tools might touch this repo at the same time again, a separate clone/worktree per tool would avoid the entanglement entirely. The Java 25 upgrade itself was legitimate, verified, working, and is now the live state of both `mainline` and the deployed backend.
